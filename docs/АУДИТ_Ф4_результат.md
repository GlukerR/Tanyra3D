## Задача 1. Добавить площадку — 1 файл

Положил `profiles/<id>.json`, перечитал модуль начисто, спросил ассистента:

```
имя файла = id  (как у встроенных)
   в списке: да   выбор работает: да   опции: 14 шт
```

Площадка появляется, выбирается, отдаёт свои 14 опций. Код не трогается, `core/` не
трогается. Механизм — `readdirSync` (`assistant.mts:168`), плюс вторая папка рядом с
настройками приложения и переменная `TANYRA3D_PROFILES_DIR`. **Доктрина держится.**

### Находка Ф4-1: площадка видна в списке, но падает при выборе

Тот же пробник, два других сценария:

```
имя файла ≠ id  (контрибутор назвал файл иначе)
   в списке: да   выбор работает: ПАДАЕТ: Unknown platform "f4probe". Available: google-store, shopify…
id кириллицей   (площадка «Авито»)
   в списке: да   выбор работает: ПАДАЕТ: Unknown platform "авито". Available: google-store, shopify…
```

Это **вид 1 по классификации плана — дубль факта.** Один и тот же вопрос «какие площадки
есть» решается двумя разными способами:

- `listPlatforms()` (`assistant.mts:456`) читает поле `id` ИЗНУТРИ каждого файла;
- `profilePath()` (`assistant.mts:187`) ищет файл ПО ИМЕНИ: `` `${safeId(id)}.json` ``.

Совпадают они ровно до тех пор, пока имя файла равно `id`. А `safeId` (`assistant.mts:175`)
вдобавок вырезает всё, кроме `[a-z0-9_-]`, — то есть кириллический `id` не загрузится
никогда, хотя в списке будет виден.

Требование «файл называется `<id>.json`» записано — `docs/ARCHITECTURE.md:568`, по-английски,
в разделе про добавление профиля. То есть доктрина есть, но **не проверяется и не
подсказывается**.

Хуже всего текст ошибки: `Unknown platform "авито". Available: … авито.` Сообщение
называет площадку недоступной и в той же строке перечисляет её среди доступных, потому что
список для сообщения строится первым способом, а поиск шёл вторым. Контрибутор, читающий
эту строку, ищет опечатку там, где её нет.

## Задача 2. Добавить правило — 3 файла наблюдению, 7 опции

Правила живут массивом `RULES` (`addons/gltf/rules.mts:546`, 24 правила, файл на 2317
строк). Отдельного файла на плагин нет.

**Это не дрейф, а записанное решение**, и аудит обязан это сказать. `docs/EXTENDING.md` §4:
до 1.0 форма плагина внутренняя и ломается свободно, а массив `RULES` назван «уже семенем»
плагинной системы. Мерить проект против системы, которую он сознательно отложил, — нечестно.

**Правило-наблюдение** (без флажка, как `scene/lod-levels`) — 3 файла:

1. `addons/gltf/rules.mts` — само правило;
2. `addons/gltf/messages/en.mjs` — строки под `titleKey`;
3. `addons/gltf/messages/ru.mjs` — то же.

Замер каталогов: 24 правила, 24 `titleKey`, **ни одного отсутствующего** в `en.mjs`.
Дисциплина соблюдается.

**Правило-опция** (человек включает флажком) — 7 файлов, и вот где счёт растёт:

4. `addons/gltf/index.mts` — запись в `ADVANCED_FEATURES` (сейчас их 14);
5. `engines/threejs.json` — `availableExtensions`;
6. `engines/model-viewer.json` — то же;
7. **`ui/app.ts`** — таблица `OPT_GROUPS` (`ui/app.ts:999`).

### Находка Ф4-2: интерфейс держит собственную таблицу опций

`OPT_GROUPS` перечисляет id фич поимённо и решает, в какую визуальную группу попадёт
опция:

```ts
{ titleKey: 'group.cleanup',    kind: 'checks', ids: ['safe', 'strip-colors'] },
{ titleKey: 'group.structural', kind: 'checks', ids: ['join', 'instance'] },
{ titleKey: 'group.textures',   kind: 'checks', ids: ['ktx2', 'webp'] },
{ titleKey: 'group.textureSize', kind: 'textureSize', ids: ['resize-512', …] },
{ titleKey: 'group.animation',  kind: 'checks', ids: ['resample'] },
```

Опция, которой нет в этой таблице, не попадёт ни в одну группу. Замер подтверждает охват:
**все 14 id фич из `ADVANCED_FEATURES` встречаются в `ui/app.ts`** — не в комментариях, а в
работающих строках (группы, выбор кодека `1365–1367`, умолчания `2288–2291`, подпись
источника `2307–2314`).

Это **вид 3 — знание не по слою** и **вид 4 — список в коде вместо данных** сразу.

Оговорка в пользу проекта, и существенная: рядом, `ui/app.ts:1012`, лежит комментарий о
том, что зашитый список `needsDecoder = ['meshopt','draco','ktx2','instance']` из этого же
файла уже был убран 2026-08-10 — ровно по этой причине и с той же формулировкой («второй
список одной правды расходится молча»). Приём известен и однажды применён; `OPT_GROUPS`
просто не дошла очередь.

## Задача 3. Добавить движок — 1 файл

```
движки:  f4engine, threejs, model-viewer
виден:   true
опции с прочерком: 14 шт
```

`engines/<id>.json`, находится сканом папки (`assistant.mts:328`). Код не нужен.

Оговорка: движок объявляет поле `viewer`, и оба нынешних движка указывают на один и тот же

Обращение с чужим значением сделано мягко и правильно: неизвестный вьюпорт не роняет
приложение, а пишет в журнал и остаётся на прежнем (`ui/viewer/index.ts:48–51`).

## Задача 4. Добавить язык — 2 файла на витрину, 9 на настоящий (после правки — 5)

Положил `translations/de.js` и `translations/validator-de.js` — ровно то, что велит
`ui/locales/README.md` («Adding a language means putting two files into `translations/`.
Nothing else»). Замер:

```
1. кнопка языка в шапке        : появится (сервер сканирует папку)
2. языки отчёта listLanguages(): en, ru
   немецкий среди них          : НЕТ
3. названия площадок (de)      : Google Store, Shopify, VNTANA
   описание площадки (de)      : Google's own hardware pages: the product spin…
4. подписи опций (de)          : Safe optimizations | Meshopt compression
```

Кнопка появляется, обвязка интерфейса переводится — и на этом язык кончается. Всё, что
считает сервер (описания площадок, подписи опций, книжечки 📖, строки отчёта, «что
сделано»), остаётся английским.

### Находка Ф4-3: каталоги языков сервера зашиты импортами — единственное место, где нужен `core/`

Три файла кода жёстко перечисляют языки:

| файл | строки |
|---|---|
| `assistant.mts` | `31–32` импорты + `107` `const CATALOGS = { en, ru }` |
| **`core/engine.mts`** | `23–24` импорты + `27–28` `register('en'…) register('ru'…)` |
| `addons/gltf/index.mts` | `28–29` импорты + `115–116` `register(…)` |

Контраст резкий и он внутри одного проекта. Площадки, движки и локали ИНТЕРФЕЙСА находятся
сканом папки; каталоги сервера — статическими импортами. Механизм для динамики уже есть и
работает: `core/i18n.mts:36` `register(locale, messages)` принимает любой код языка, его
никто не ограничивает. Не хватает только того, кто прочитает папку.

Это **вид 4** в чистом виде и единственный случай во всём Ф4, где контрибутор обязан
открыть `core/`.

### Находка Ф4-4: README обещает больше, чем делает, и сам себе противоречит

`ui/locales/README.md` говорит «Nothing else», а через несколько абзацев — «The
form-selection rule for a new language is added to `plural()` in `ui/i18n.js` — that is the
only place where a code change may be needed». Для языка с тремя формами множественного
числа (польский, чешский) это не «may be», а обязательное.

Про три серверных каталога README упоминает («What this catalog does NOT translate»), но не
называет их ценой добавления языка. Человек, прочитавший инструкцию буквально, положит два
файла и получит наполовину английское приложение — ровно то, что показал замер.

Честный состав полного немецкого — **9 файлов**, из них 3 кода:

```
translations/de.js                 translations/validator-de.js
messages/de.mjs                    + правка assistant.mts
core/messages/de.mjs               + правка core/engine.mts      ← ядро
addons/gltf/messages/de.mjs        + правка addons/gltf/index.mts
```

Профили и движки (`de` в `description`) не считаю: `pick()` (`assistant.mts:126`) честно
откатывается на английский, и это осознанное решение — «требовать от стороннего профиля
перевода на все языки значит не получить сторонних профилей».

## Задача 5. Добавить формат на вход — 7 файлов

Список входных форматов записан руками **в пяти местах**:

| файл | что там |
|---|---|
| `addons/gltf/importers.mts:40` | `IMPORT_FORMATS = ['stl','ply','fbx','obj']` — первоисточник |
| `server.mts:774` | `MODEL_EXT = /\.(glb\|gltf\|stl\|ply\|fbx\|obj)$/i` |
| `ui/app.ts:287` | `MODEL_RE` — та же регулярка |
| `ui/index.html:124` | `accept=".glb,.gltf,.stl,.ply,.fbx,.obj"` |
| `ui/viewer/viewer.ts:36` | `FOREIGN_FORMATS = ["stl","ply","fbx","obj"]` |

Плюс разбор (новый `import-<fmt>.mts` или ветка в `importers.mts`) и ветка загрузки во
вьюпорте. Итого 7 файлов, `core/` не тронут — реестр ядра берёт форматы у аддона
(`addons/gltf/index.mts:1363`).

**И вот здесь проект выглядит лучше, чем можно было ожидать.** Дубль есть, но он
**сторожится**: `tests/import-stl-ply.test.mjs:330–370` сверяет все пять списков между
собой, а отдельная проверка требует, чтобы каждый ПРИНИМАЕМЫЙ формат умел ПОКАЗЫВАТЬСЯ —
она заведена после дефекта с FBX, который принимался, но не рисовался. Расхождение не
пройдёт молча.

То есть по классификации это дубль факта (вид 1), но с закрытым риском. Разница с находкой
Ф4-1 принципиальная: там дубль не сторожится ничем.

### Побочное наблюдение для Ф6

Эти сторожа сверяют **текст исходника регуляркой** — `/const FOREIGN_FORMATS = \[([^\]]+)\]/`
и подобные. И читают они `server.mjs` и `ui/app.js`, то есть **выводы сборки, а не
исходники** `.mts`/`.ts`. Контрибутор, поправивший `server.mts` и не запустивший сборку,
получит проверку по старому файлу. Это материал фазы Ф6, здесь только помечено.

## Что сделано по итогам (2026-08-26, ветка `fix/audit-f4`)

Три находки из четырёх закрыты в тот же день по слову Александра «правь и иди дальше».

**Ф4-1 — закрыта.** Ответ на вопрос «какие площадки есть» стал один: `profileEntries()`
(`assistant.mts`) читает папку и отдаёт id ИЗНУТРИ файла, а `profilePath()` и
`listPlatforms()` оба ходят через него. Поиск по имени файла остался быстрым путём (ни
одного чтения на обычном случае), а по id — запасным. Сторож — `tests/user-profiles.test.mjs`,
раздел «площадка находится по id, а не по имени файла»; проба на красноту пройдена.

Побочно вскрылась вторая дыра, которую прятал `any`: `listPlatforms()` возвращал `id`
нетипизированным (он приходил из `JSON.parse`), и `(список[0] || {}).id` при ПУСТОМ списке
площадок давал `undefined`, который уезжал в `planFor` как имя площадки. Типизация сделала
это видимым, фолбэк исправлен на прочерк (`server.mts`).

**Ф4-3 — закрыта, и это снимает единственную зависимость от `core/`.** Появился
`loadCatalogs()` (`core/i18n.mts`): читает ПАПКУ каталогов и регистрирует всё, что нашёл.
Три статических перечня языков удалены — из `core/engine.mts`, `addons/gltf/index.mts` и
`assistant.mts`. Проверено действием: копия русского каталога, положенная в три папки, даёт
`listLanguages() → de, en, ru` и настоящие немецкие строки в ядре и в правилах.

Цена — один вычисленный `import()` (модуль по вычисленному пути в ESM иначе не грузится).
Архитектурный гейт `tests/architecture/layer-boundaries.test.mjs` такие импорты считает
слепым пятном и покраснел — правильно сделал. Исключение выдано ПОИМЁННО
(`DYNAMIC_CATALOG_LOADERS`, два файла) и снабжено собственным сторожем: он требует, чтобы
каждый файл списка такой импорт действительно содержал, и чтобы список не рос молча.
Проверено пробой: вычисленный `import()` в `optimize2.mjs` гейт по-прежнему ловит.

**Ф4-4 — закрыта.** `ui/locales/README.md` больше не обещает «Nothing else». Написано
прямо: два файла дают обвязку интерфейса, полный язык стоит пяти файлов, и все пять —
данные. Таблица «какой файл что переводит» на месте, оговорка про `plural()` сужена до
языков, у которых формы множественного числа отличаются от английских и русских.

**Ф4-2 (`OPT_GROUPS`) — НЕ трогал, и намеренно.** Это самая дорогая находка и единственная
спорная: группа опции — свойство ПОКАЗА, и кому принадлежит это знание, решается не
попутной правкой. Материал переходит в Ф3, где вопрос «какие словари знает слой `ui`»
разбирается целиком.
