# План аудита: хардкод и путь контрибутора

Заказ Александра, 2026-08-26: «Я боюсь что у нас всё больше и больше хардкода и мы можем
уходить от удобного для контрибуторов приложения. Надо составить план проверки всего
приложения даже если на это уйдёт уйма времени».

Формат он выбрал: **сначала отчёт, правки — по его решению.** Аудит ничего не ломает,
пока он не сказал.

---

## 0. Что именно мы ищем

«Хардкод» — слово размытое, и с ним аудит превращается во вкусовщину. Поэтому ищем
ЧЕТЫРЕ названных вида, и у каждого своя проверка. Три из четырёх найдены за один день
26 августа — это не гипотезы, а образцы.

### Вид 1. Дубль факта

Один и тот же факт записан в двух местах, и места расходятся молча.

> **Образец.** `REPO_MODELS` в `tests/helpers/model-files.mjs` — рукописная копия того,
> что уже сказано в `fixtures/.gitignore`. Разошлись дважды: две коммитимые модели не
> попали в список и на CI считались локальными, то есть молча пропускались. Одна из них
> заводилась ровно затем, чтобы сторож скиннинга гонялся на чистом клоне.

**Почему опасен:** расхождение беззвучное. Тесты зелёные, поведение неверное.

### Вид 2. Чужое чтение

Поле заполнено для одной цели, а читается для другой.

> **Образец.** `baselineOpts.codec` — план сборки движка, заполнен У ВСЕГО: у прочерка,
> у самого движка, у каждого профиля. Прочитан как СОВЕТ человеку — и совет получился
> всегда, включая площадку, чей профиль сам называет вопрос открытым.

**Почему опасен:** оба чтения выглядят разумно по отдельности. Ошибка видна, только если
спросить «а для чего это поле заполняли».

### Вид 3. Знание не по слою

Слой знает имена, принадлежащие другому слою.

> **Образец.** Шесть имён расширений glTF (`EXT_texture_webp`,
> `KHR_draco_mesh_compression` и далее) лежат в `ui/app.ts`. До 26 августа в слое
> интерфейса не было ни одного — добавлены в тот день. На втором движке (0.3.0) это
> придётся разбирать.

**Почему опасен:** не мешает сегодня и стоит дорого завтра — ровно когда появится второй
движок или второй формат.

### Вид 4. Список в коде вместо данных

Перечень, который контрибутор ожидает найти в данных, лежит в коде.

**Почему опасен:** это и есть «неудобно для контрибуторов» в чистом виде: чтобы добавить
площадку или правило, приходится править код, а не положить файл.

### Чего НЕ ищем

- Магические числа сами по себе. Порог, объяснённый в комментарии и покрытый тестом, —
  не дефект.
- Длинные файлы сами по себе. Длина — симптом; в Ф5 меряем швы, а не строки.
- Красоту. Аудит про сохранность и про порог входа, не про вкус.

## Ф1. Карта данных: кто заполняет и кто читает

**Ищет:** вид 2.

Для КАЖДОГО поля в `profiles/*.json`, `engines/*.json` и каждой таблицы-константы в коде
выписать три столбца:

| поле | кто заполняет и ЗАЧЕМ | кто читает и ЗАЧЕМ |
|---|---|---|

**Критерий дефекта:** цель заполнения и цель чтения не совпадают. Именно так вскрылся
`baselineOpts.codec`.

**Выход:** таблица целиком плюс список расхождений.
**Стоимость:** высокая, делается один раз, дальше поддерживается.
**Начинать с** `profiles/`: там поле видно глазами, и там уже нашлось.

## Ф2. Дубли фактов

**Ищет:** вид 1.

Метод — от каждого перечня в коде задать вопрос: **этот факт где-то уже записан?**
Кандидаты, видные заранее:

- `SOURCE_MARKERS` (`ui/app.ts`) — знание аддона о расширениях, переписанное в интерфейс;
- `DECODER_KEYS`, `TEXTURE_SLOTS` и прочие таблицы `ui/app.ts`;
- списки моделей в тестах (`GOLDEN_MODELS`, `LOCAL_ONLY`, `KNOWN_HOLES`);
- `exclusiveGroups` — уже расходился однажды и был починен; проверить, не завёлся ли снова.

**Критерий дефекта:** факт выводится из другого источника, но переписан руками.

**Правило починки:** не «синхронизировать», а **удалить копию** и читать первоисточник.
Синхронизация — тот же дубль плюс обязанность помнить.

**Выход:** список дублей с указанием первоисточника.

## Ф3. Протечка имён между слоями

**Ищет:** вид 3.

Для каждого слоя (`core/`, `addons/gltf/`, `ui/`, `ui/viewer/`, `server.mts`,
`assistant.mts`, `profiles/`) посчитать, какие чужие словари он знает:

- имена расширений glTF (`KHR_*`, `EXT_*`);
- id фич (`safe`, `join`, `meshopt`…);
- имена движков (`threejs`, `model-viewer`);
- имена площадок.

**Критерий дефекта:** слой знает словарь, который по `docs/ARCHITECTURE.md` §4b/§4g ему
не принадлежит.

**Замер уже сделан 2026-08-26:** в `ui/app.ts` шесть имён расширений glTF, все шесть
добавлены в тот день. Остальные слои не мерены.

**Выход:** таблица «слой × словарь × сколько» и список нарушений.

## Ф4. Путь контрибутора — измеряется ДЕЙСТВИЕМ, а не чтением

**Ищет:** виды 3 и 4 сразу, и отвечает на вопрос Александра прямо.

Не рассуждать, а **проделать пять задач** и посчитать, сколько файлов пришлось тронуть и
был ли среди них `core/`:

| задача | сколько файлов | тронут ли core | нужен ли код |
|---|---|---|---|
| добавить площадку | | | |
| добавить правило-плагин | | | |
| добавить движок | | | |
| добавить язык | | | |
| добавить формат на вход | | | |

**Критерий:** по доктрине (`docs/EXTENDING.md`) первые две задачи — это ДАННЫЕ и один
файл плагина, без правки ядра и интерфейса. Если на деле файлов больше — это и есть
измеренный ответ, насколько мы ушли.

**Выход:** пять чисел. Самая честная метрика во всём аудите: её нельзя оспорить вкусом.

## Ф5. Швы: почему `ui/app.ts` на 5848 строк

**Ищет:** вид 4 и границы.

Длина сама по себе не дефект. Дефект — если файл нельзя разрезать, потому что всё
связано со всем. Поэтому меряем не строки, а **швы**: сколько в файле независимых
областей и что мешает вынести каждую.

Размеры на 2026-08-26, для отсчёта:

| файл | строк |
|---|---|
| `ui/app.ts` | 5848 |
| `addons/gltf/rules.mts` | 2317 |
| `server.mts` | ~1800 |
| `ui/viewer/viewer.ts` | 1413 |
| `addons/gltf/index.mts` | 1385 |

**Критерий:** область, у которой нет входящих связей кроме двух-трёх вызовов, — готовый
шов. Область, завязанная на десяток переменных модуля, — не шов, и резать её нельзя.

**Выход:** список швов с оценкой и честное «остальное не режется, потому что…».

## Ф6. Тесты: держатся за поведение или за текст исходника

**Ищет:** барьер для контрибутора, который бьёт сильнее остальных.

Много сторожей проекта сверяют ТЕКСТ исходника регуляркой — в том числе почти все,
написанные 26 августа. Контрибутор переименовывает переменную и получает красноту, не
сломав ничего.

**Метод — эксперимент, а не мнение.** Переименовать две-три переменные, ничего не меняя
по сути, прогнать набор, посчитать красные. Число и есть ответ.

**Критерий:** сторож, краснеющий от чистого переименования, обязан либо давать внятное
сообщение «якорь сменился, обнови», либо быть переписан на поведение.

**Замечание честности:** это самая неприятная часть аудита для меня — большинство таких
сторожей написал я, и защищать их вкусом нельзя. Мерить надо экспериментом.

**Выход:** число красных на переименование и список сторожей, которые стоит переписать.

## Ф7. Отчёт

Один документ: находки по видам, у каждой доказательство — файл, строка, замер. Никаких
«кажется». Правки — отдельным заходом, по решению Александра.

## Правила проведения

1. **Не чинить по ходу.** Найденное записывается, а не правится: иначе аудит превращается
   в переписывание, а отчёта не получается. Исключение — мёртвый код, который уже ничем
   не читается.
2. **У каждой находки доказательство.** Файл, строка, замер. «Выглядит как хардкод» —
   не находка.
3. **Замер, а не память.** Ровно в этот день трижды подтвердилось, что память врёт:
   `grep` на `ui/app.ts` молча обрывался на нулевом байте (`const NAME_SLOT = '\0'`),
   `server.mjs` оказался выводом сборки, а не исходником, и правка в него бесследно
   исчезла при следующей сборке.
4. **Считать надо и то, что найдено у себя.** Три из четырёх образцов в разделе 0 — мой
   собственный код за один день. Аудит, щадящий автора, бесполезен.
