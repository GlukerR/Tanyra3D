## 1. Проблема: интеграционные тесты защищают поведение, а не архитектуру

Набор тестов на момент написания: ~718 node + ~74 browser (к 2026-08-19 — около 4 000
в 84 файлах; вывод от этого не меняется, а числа ниже читать как тогдашние). Все они
интеграционные: настоящие модели через настоящий пайплайн (`optimizeFile`), без моков.
Это отлично защищает *поведение* — но не защищает *архитектуру*.

Пример из разбора. Если завтра в `core/engine.mjs` появится
`import * as THREE from 'three'` — все 718 тестов продолжат проходить: пайплайн-то
работает. Архитектурное обещание «ядро не знает ни про three.js, ни про glTF»
нарушено, а гейт молчит. Обе агентские модели сошлись в диагнозе: **следующий этап
зрелости проекта — защита архитектуры как контрактов, а не только поведения**.

С этим диагнозом документ согласен полностью. Расхождения — в механике лечения.

## 2. Что уже защищено (факты, проверены по коду)

Прежде чем добавлять новые гейты, надо зафиксировать, что уже есть — иначе план
будет «строить то, что уже построено».

### 2.1. Направление зависимостей уже инвертировано

- `core/` импортирует **только** `node:*` и собственные модули
  (`./contract.mjs`, `./i18n.mjs`, `./messages/*`). Ни three, ни gltf-transform,
  ни addons.
- `addons/gltf/` импортирует **core** (`../../core/contract.mjs`,
  `../../core/i18n.mjs`) — зависимость идёт от аддона к ядру, а не наоборот.
- Склейка происходит в `optimize2.mjs` (composition root):
  `runOptimize(addon, srcPath, opts)` — **аддон передаётся движку параметром**
  (внедрение зависимости, `core/engine.mjs:94`).

Это значит: опасное ребро не «Core → GLTFProvider» (оно структурно невозможно —
аддон впрыскивается), а **«core → three / @gltf-transform / addons»**. Если кто-то
напишет `import gltfAddon from '../addons/gltf/index.mjs'` внутри `core/engine.mjs`
— инъекция обойдена, и это ровно тот случай, который надо ловить.

### 2.2. Шов второго формата уже существует

`core/registry.mjs` — готовый `register(addon)` / `resolve(path)` / `addons()`.
`register` валидирует `addon.formats` (непустой массив). В коде есть комментарий:
«форматы (FBX/USD/...) уже здесь: register(addon) + resolve(path)».

Вывод для плана: задача не «сделать Plugin API», а **защитить существующий**.

### 2.3. Мета-гейты в тестах уже есть

Проект уже любит сторожевые тесты, и `tests/architecture/` ляжет в этот стиль:

| Гейт | Что сторожит |
|---|---|
| `locale-keys-symmetry.test.mjs` | симметрия каталогов EN/RU (4 пары) |
| `analyse-baseline.test.mjs` + `analyse-test-coverage.mjs` | число тестов ≥ baseline, модели на диске, покрытие |
| `report-density.test.mjs` | одна запись на класс случаев, не «толпа строк» |
| `report-honesty.test.mjs` | причина пропуска — настоящая |
| `russian-locale.test.mjs` | белый список терминов, нет непереведённого |
| golden-corpus | whitelist ruleIds строится из `listRules()` (правило 11: «сверять с кодом, а не с файлом») |

Плюс дисциплина в самих тестах: тестам **запрещено** импортировать внутренности
(`@gltf-transform/core`), они читают GLB-контейнер напрямую. Это уже
архитектурная культура — не хватает только механического гейта на границы слоёв.

### 2.4. Реальный граф импортов (проверено 2026-08-03)

| Слой / файл | Импортирует | Запрещено |

## 3. Разбор Агента №1 (предложение: категория `tests/architecture/`)

### Что верно

1. **Главный тезис верен на 100%:** интеграционные тесты не ловят нарушение
   границ слоёв. `core → three.js` пройдёт весь набор.
2. **Циклические зависимости** — да, ESM ловит только часть циклов (функции с
   hoisting переживают цикл); статическая проверка графа дёшева и полезна.
3. **Публичный API** — контракт RunResult формализован в ARCHITECTURE.md §4b
   («добавлять поля можно, переименование — ломающее изменение»), но закреплён
   только косвенно (часть полей проверяется в `optimize.test.mjs` и golden-corpus).
   Отдельного контрактного снимка нет.
4. **Приоритизация:** не спешить с mutation testing, fuzzing, property-based и
   performance-регрессиями — сейчас они дадут меньше пользы, чем гейт границ.

### Что неверно (с фактами)

1. **Ментальная модель проекта не совпадает с реальностью.** Агент предполагал
   «core ↓ providers», т.е. ядро знает провайдеров. В проекте всё наоборот:
   аддон впрыскивается параметром (`runOptimize(addon, ...)`), а аддон сам
   импортирует core. Опасные рёбра — другие (см. §2.1).
2. **«Проверить, что Core не импортирует Viewer» — тривиальный пример**, ценность
   не в нём. Коронный тест — «движок работает на выдуманном формате» (мок-аддон),
   который проверяет архитектурное *обещание*, а не структуру файлов. Агент это
   не назвал.
3. **«Проверить, что все Providers реализуют интерфейс»** — интерфейс аддона уже описан
   в `core/types.mts` и — главное — **вызовами `addon.*` в `core/engine.mts`**. Оракул
   контракта — исходник движка, не документ. (Написано, когда ядро было целиком на JS и
   компилятора не было вовсе; с 2026-08-11 ядро на TypeScript, но вывод не изменился:
   аддон типы не обязан импортировать, а вызовы движка обойти нельзя.)
4. **Агент не заметил registry** (§2.2) — предложение звучало так, будто плагинной
   системы нет, хотя она есть и её надо защищать, а не строить.

## 4. Разбор Агента №2 (правки к Агенту №1)

### Принято

1. **Два уровня защиты ортогональны** и оба нужны: мок-аддон проверяет *поведение*
   (движок работает на чужом формате), границы импортов — *структуру* (никто не
   принёс запрещённое ребро). Один не заменяет другой.
2. **«Защитить существующий Plugin API», а не «сделать»** — да, объём работы меньше.

### Отклонено / исправлено

1. **«Границы — через AST, а не regex».** Направление верное, инструмент — нет.
   Факт: `acorn`, `oxc-parser`, `@babel/parser` в дереве зависимостей ОТСУТСТВУЮТ
   (`npm ls` пусто, проверено 2026-08-03). Полный AST-парсер ради извлечения строк
   `import` — новая зависимость, противоречащая принципу ЗАВИСИМОСТИ.md («не
   выдумываем из головы — используем проверенные библиотеки»).
   Правильный инструмент — **`es-module-lexer@2.3.1`, который уже лежит в дереве**
   (транзитивная зависимость vitest). Это ровно тот лексер, которым Vite разбирает
   импорты: он штатно обрабатывает `import(...)`, `export * from`, многострочные
   импорты, кавычки, комментарии. Достаточно промоутнуть его в прямую
   devDependency и задокументировать в ЗАВИСИМОСТИ.md.
   Оговорка, которую не дал ни один агент: **`import(variable)` с динамическим
   спецификатором не увидит и AST** — это неразрешимо статически в принципе.
   Приемлемо: в коде таких импортов нет, сторож ловит 99% реальных регрессий.
2. **Порядок.** Агент поставил границы первыми, мок-аддон вторым. Автор ставит
   **мок-аддон первым**: он доказывает главное обещание проекта, и если бюджет
   режут — его нельзя резать. Границы — дешёвая страховка от случайности.
   Оба гейта дешёвые, порядок не критичен, но приоритет зафиксирован.
3. **Overlap.** Агент любит «не плодить дубли», но сам же предложил public-api
   тест, частично существующий (`optimize.test.mjs`, golden-corpus). Правильно —
   **консолидировать** в один контрактный снимок, а не писать четвёртый файл с
   теми же проверками.

## 5. Вердикт и план гейтов

### Принцип: два уровня защиты

- **Поведенческий** — мок-аддон на выдуманном формате: если движок действительно
  формат-агностичен, `runOptimize(fakeAddon, ...)` вернёт корректный RunResult, не
  зная про glTF. Это проверка архитектурного обещания, а не реализация.
- **Структурный** — статический скан графа импортов: запрещённые рёбра падают
  за секунду. Это страховка от случайной ошибки будущего участника.

### Гейты (по приоритету)

1. **`addon-contract.test.mjs`** — коронный.
   - Сканируем `core/engine.mjs` на вызовы `addon.*`: `outputName`,
     `normalizeOpts`, `createIO`, `load`, `collectMetrics`,
     `stripInputCompression`, `rules`, `baselineMetrics`, `BASELINE_METRICS`,
     `writeBytes`, `readBytes`, `validate`, `writeReport`.
   - Строим от этого набора мок-аддон (метод-сет выводится из исходника движка,
     а не из документации — иначе фейк недописан и тест падает по неверной
     причине).
   - Прогоняем `runOptimize` на выдуманном формате — доказываем
     формат-агностичность.
   - Сверяем, что реальный `addons/gltf/index.mjs` реализует каждый вызванный
     метод. Контракт живёт в коде, а не в комментарии.

2. **`layer-boundaries.test.mjs`** — `es-module-lexer` + allow-list по слоям
   (правила — ровно таблица §2.4): `core/*` → только `node:*` и `core/*`;
   `addons/*` → не `ui/`, не `optimize2.mjs`, не `server.mjs`, не `assistant.mjs`;
   `ui/` → не core/addons; **правило composition root**: проводку core+addons
   имеют право держать только `optimize2.mjs` и `server.mjs`.

3. **`registry.test.mjs`** — register/resolve/addons, включая регистрацию
   второго формата (шов под FBX/USD из §2.2).

4. **`public-api.test.mjs`** — контрактный снимок RunResult / listRules /
   assistant-экспортов. Консолидация существующих проверок, без дублей.

5. **`no-cycles.test.mjs`** — DFS по графу импортов (тем же лексером).

### Чего НЕ добавлять сейчас

Согласие с обоими агентами: mutation testing, property-based, fuzzing,
performance-регрессии — позже. Оговорка: «число тестов раздуто» к проекту почти
неприменимо — рост числа это осознанная матрица «модель × комбинация флагов», а
не дубли; от дублей-строк уже есть `report-density`.
