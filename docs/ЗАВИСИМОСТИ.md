### Компонент: draco3dgltf (v1.5.7)

**GitHub:** https://github.com/google/draco/tree/gltf_2_draco_extension  
**Версия в проекте:** 1.5.7  
**Документация:** https://github.com/google/draco (главный репо), глава glTF  
**Как используем в проекте:** `@gltf-transform/functions → fns.draco()` для сжатия геометрии (advanced feature: `--draco`).  
**Издатель:** Google Draco Team

**Ключевые гарантии / поведение:**

- **Квантизация вершин:** Draco сжимает координаты вершин приведением к целочисленной сетке. Точность позиций от этого падает, количество вершин — нет.

- **Треугольники нулевой площади кодировщик ВЫБРАСЫВАЕТ.** Здесь до 2026-08-22 стояло
  обратное утверждение («Draco НЕ меняет количество треугольников, любое расхождение —
  результат других правил»), и оно было неверным. Замер по 61 настоящей модели:

  ```
  потеряно треугольников = (тройки с повторяющимся ИНДЕКСОМ)
                         + (тройки, у которых два угла в одной ТОЧКЕ при разных индексах)
  ```

  Сходилось до единицы на всех проверенных (Whatsminer 2 + 17558 = 17560; Е300
  213 + 192 = 405; подземка6 160 + 0 = 160; лифт 50 + 14 = 64). Треугольники, вырожденные
  лишь по коллинеарности (три РАЗНЫЕ точки на одной прямой), кодировщик оставляет: на тех
  же моделях их было 124 и 41, и до записи они дожили.

  Важно, чего в этом НЕТ: от числа бит квантования (проверено на 11, 14, 16, 20) потеря не
  зависит вовсе. То есть сетка ни при чём — выбрасываются те треугольники, которые уже были
  нулевой площади во входном файле.

  Следствие для нас: такие треугольники убирает правило `geometry/degenerate-triangles` в
  БАЗОВОМ проходе, до снимка baseline-checkpoint. Тогда кодировщику терять нечего и сверка
  сходится. Сторож — `tests/degenerate-triangles.test.mjs`.

- **Анимация и скины:** Draco сжимает только геометрию (позиции, нормали, теккоорды). Анимация, скины, morph targets кодируются отдельно и остаются нетронуты.

- **Лосси-ность:** Draco по умолчанию компрессивен с потерей (lossy), но потеря контролируется квантизацией позиций. При стандартных настройках (11 бит для позиций) потеря минимальна и в большинстве случаев визуально незаметна.

- **Обратимость:** Draco можно снять (распаковать) обратно в стандартную геометрию. Это происходит автоматически при загрузке глтф с расширением `KHR_draco_mesh_compression`. Переупаковка Draco в Draco (re-encoding) **накапливает потери** и не рекомендуется (ARCHITECTURE.md §6).

**Для нашей валидации (baseline metrics):**

- Может изменить геометрию: **Да, в одном виде** — выбрасывает треугольники нулевой площади (см. выше). Поэтому их убираем мы сами, до снимка baseline-checkpoint. Всё остальное — количество и топологию — сохраняет.
- Может изменить структуру mesh: **Нет**, примитивы и аксессоры остаются.
- Потеря данных: **Minor** (точность позиций / нормалей, но визуально незаметно при стандартных параметрах).
- Гарантия: количество вершин, индексов, примитивов, сценография, анимация, скины — неизменны.

**Источники:**
- https://github.com/google/draco/blob/1.5.7/README.md
- Интеграция в glTF-Transform: https://gltf-transform.dev/functions#draco

### Компонент: @gltf-transform/core (v4.4.1)

**GitHub:** https://github.com/donmccurdy/glTF-Transform  
**Версия в проекте:** 4.4.1  
**Документация:** https://gltf-transform.dev/  
**API Reference:** https://gltf-transform.dev/classes/Document  
**Как используем в проекте:** Главный SDK. Все операции идут через `Document` (in-memory граф glTF), загрузка через `NodeIO`, трансформации через `document.transform(fn)`.  
**Издатель:** Don McCurdy

**Ключевые гарантии / поведение:**

- **Парсинг и сохранение:** Полная поддержка glTF 2.0 и расширений (KHR_* и EXT_*). Автоматически разрешает внешние буферы/текстуры и выходит как единый GLB.

- **Трансформации (Functions):** Каждая функция из `@gltf-transform/functions` гарантирует конкретное поведение:
  - `dedup()` — склеивает идентичные текстуры и материалы (структурно безопасно, не меняет вид).
  - `prune()` — удаляет неиспользуемые ресурсы (безопасно для рендера, но может менять индексы аксессоров).
  - `weld()` — объединяет вершины на epsilon-расстоянии (numeric, может порождать вырожденные треугольники).
  - `meshopt()` — вызывает кодер Meshopt (numeric, не меняет топологию).
  - `draco()` — вызывает кодер Draco (numeric, не меняет топологию).
  - `ktx2()` — кодирует текстуры в KTX2 (perceptual, контролируется параметром качества).

- **Working copy model:** Все трансформации происходят на копии Document в памяти. Исходный файл никогда не меняется.

- **Inspect (метрики):** Функция `inspect(doc)` возвращает структурированную информацию о модели (треугольники, draw calls, размеры текстур на диске и VRAM).

**Для нашей валидации:**

- Каждая функция в `@gltf-transform/functions` задокументирована с точными семантиками.
- Гарантия: если `meta.fixSafety` правила правильно указан, трансформация будет в своём слое (provable не ломает семантику, numeric/perceptual не гарантирует бит-идентичность).

**Источники:**
- https://gltf-transform.dev/functions
- https://gltf-transform.dev/classes/Document

### Компонент: @gltf-transform/extensions (v4.4.1)

**GitHub:** https://github.com/donmccurdy/glTF-Transform (тот же репо)  
**Версия в проекте:** 4.4.1  
**Документация:** https://gltf-transform.dev/extensions  
**Как используем в проекте:** Регистрация расширений при инициализации `NodeIO`, включая `KTX2Extension` для кодирования/декодирования KTX2 текстур.  
**Издатель:** Don McCurdy

**Ключевые гарантии / поведение:**

- **KTX2 (через EXT_texture_webp и KHR_texture_basisu):** Текстуры кодируются в контейнер KTX2 с алгоритмом BASIS-U (ETC1S для цвета, UASTC для деталей). Потеря качества зависит от параметра:
  - **ETC1S** (по умолчанию для цветовых текстур): лёгкое (на диске и в VRAM), но видимое размытие для нормалей и высокочастотных деталей.
  - **UASTC** (по умолчанию для data-текстур, опционально для всех): выше качество, но больший размер в VRAM.
  - Потеря при распаковке в браузере: минимальна при качестве ≥7 (из 8).

- **Другие расширения:** Полная поддержка KHR_lights_punctual, KHR_animation_pointer, KHR_materials_* и многих других.

- **Обратимость KTX2:** Текстуры можно снять обратно в PNG/WebP (правило `decompress-ktx2`), но с потерей качества от BASIS-U сжатия.

**Для нашей валидации:**

- KTX2 меняет размер на диске и в VRAM, но не меняет количество текстур или их назначение.
- Потеря данных: **Minor** при UASTC ≥7, **Significant** при ETC1S для высокочастотных текстур.

**Источники:**
- https://gltf-transform.dev/extensions#khrtexturebasisu
- https://github.com/donmccurdy/glTF-Transform/tree/main/packages/extensions

### Компонент: @gltf-transform/functions (v4.4.1)

**GitHub:** https://github.com/donmccurdy/glTF-Transform (тот же репо)  
**Версия в проекте:** 4.4.1  
**Документация:** https://gltf-transform.dev/functions  
**Как используем в проекте:** Высокоуровневые функции трансформации: `dedup()`, `prune()`, `weld()`, `meshopt()`, `draco()`, `ktx2()`, `simplify()` и др. Вызываются через `document.transform(fn)` или напрямую.  
**Издатель:** Don McCurdy

**Ключевые функции и их гарантии:**

Каждая функция в пакете задокументирована на https://gltf-transform.dev/functions с точными параметрами и побочными эффектами. Главные для нас:

| Функция | Гарантия | Потеря | Примечание |
|---------|---------|--------|-----------|
| `dedup()` | Структурно безопасна, склеивает дубли | None | provable |
| `prune()` | Удаляет неиспользуемые ресурсы | None | provable |
| `weld(tolerance)` | Объединяет близкие вершины | Numeric (зависит от допуска) | numeric, может порождать вырожденные |
| `meshopt()` | Сжимает индексы/вершины | Minor (перестановка) | numeric |
| `draco()` | Сжимает геометрию Draco | Minor (квантизация) | numeric |
| `ktx2(…quality)` | Кодирует текстуры KTX2 | Minor/Significant (от качества) | perceptual |
| `simplify()` | Упрощает геометрию (LOD) | Significant (удаляет полигоны) | lossy |

### Компонент: gltf-validator (v2.0.0-dev.3.10)

**GitHub:** https://github.com/KhronosGroup/glTF-Validator  
**Версия в проекте:** 2.0.0-dev.3.10 (dev версия, в production используется стабильная)  
**Документация:** https://github.com/KhronosGroup/glTF-Validator/blob/main/README.md  
**API:** https://github.com/KhronosGroup/glTF-Validator/blob/main/README.md#api  
**Как используем в проекте:** Валидация входного и выходного GLB через `validator.validateBytes()`. Результат использует в отчёт фазы 4 (ВАЛИДАЦИЯ).  
**Издатель:** The Khronos Group Inc.

**Ключевые гарантии / поведение:**

- **Что проверяет:**
  1. **IoError** — ошибки ввода/вывода (например поломанный файл).
  2. **SchemaError** — нарушение JSON-схемы glTF (неверные типы, отсутствующие обязательные поля).
  3. **SemanticError** — нарушение семантики (например неверная матрица узла, несовместимые атрибуты).
  4. **LinkError** — нарушения ссылок между ресурсами (например аксессор вылезает за пределы буфера).
  5. **DataError** — нарушения в данных (например отрицательные значения в индексах анимации, деgenerate треугольники).

- **Уровни серьёзности:**
  - **Error** — блокирует спецификацию, файл невозможно корректно загрузить.
  - **Warning** — потенциальная проблема, может вызвать проблемы в некоторых движках.
  - **Information** — совет для оптимизации или совместимости, не является ошибкой.

- **Блокирующие ошибки:** ошибки Error-уровня, добавленные самой оптимизацией, дают `status: 'fail'` и красное предупреждение в интерфейсе (входные ошибки логируются как информация). Запись файла при этом **не блокируется** — решение Александра, 2026-07-30: человек должен видеть предупреждение, но сохранять право выгрузить результат.

- **Особенность:** Валидатор — версия, скомпилированная из Dart в JavaScript. Полностью соответствует официальной спецификации Khronos.

**Для нашей валидации:**

- Гарантия: ошибки Error-уровня означают нарушение спецификации (`status: 'fail'`, красное предупреждение).
- Warning / Information — логируются в отчёт, статус остаётся `ok`.
- Деgenerate треугольники — **Information**, не блокируют (общей совет).

**Источники:**
- https://github.com/KhronosGroup/glTF-Validator
- Исходный репо с полным списком ошибок: https://github.com/KhronosGroup/glTF-Validator/blob/main/ISSUES.md (скопирован в node_modules)

### Компонент: meshoptimizer (v0.22.0)

**GitHub:** https://github.com/zeux/meshoptimizer  
**Версия в проекте:** 0.22.0  
**Документация:** https://github.com/zeux/meshoptimizer (в том числе в README для JS модуля)  
**Как используем в проекте:** Сжатие геометрии через `fns.meshopt({ encoder: MeshoptEncoder })`. Также используется для оптимизации порядка индексов перед сжатием.  
**Издатель:** Arseny Kapoulkine

**Ключевые гарантии / поведение:**

- **Что сжимает:**
  - Индексные буферы (перестановка вершин для локальности, потом LZ4-подобное сжатие).
  - Вершинные буферы (атрибуты позиции, нормали, теккоорды и др.).
  - Может применять фильтры квантизации (OCTAHEDRAL, QUATERNION, EXPONENTIAL) для дополнительного сжатия данных.

- **Что НЕ меняет:**
  - Количество треугольников / вершин / индексов (остаётся то же).
  - Структура mesh (примитивы, аксессоры, материалы).
  - Анимация, скины, morph targets (они кодируются отдельно).

- **Обратимость:** Полностью обратимо без потерь (при декодировании восстанавливается оригинальные данные в пределах точности float32).

- **Производительность:** Очень быстро (1–3 ГБ/с на современных CPU). Разложен на три этапа:
  1. **reorderMesh** — переупорядочивает индексы для локальности (опционально).
  2. **quantize** / **encodeFilter** — квантизирует данные (опционально, lossy).
  3. **encode** — сжимает в конечный формат (это уже не lossy).

- **Особенность meshopt для glTF:** Вводится расширение EXT_meshopt_compression, которое браузер может распаковать на лету.

**Для нашей валидации:**

- Может изменить геометрию: **Нет**, структура и топология неизменны.
- Может изменить структуру mesh: **Нет**, примитивы и аксессоры неизменны.
- Потеря данных: **None** (если без квантизации) / **Minor** (если с квантизацией, зависит от параметра).
- Гарантия: количество треугольников, вершин, индексов неизменно.

**Источники:**
- https://github.com/zeux/meshoptimizer/blob/master/README.md (общая архитектура)
- https://github.com/zeux/meshoptimizer/blob/master/js/README.md (JS API)
- https://github.com/KhronosGroup/glTF/blob/master/extensions/2.0/Vendor/EXT_meshopt_compression/README.md (glTF расширение)

### Компонент: sharp (v0.33.5)

**GitHub:** https://github.com/lovell/sharp  
**Версия в проекте:** 0.33.5  
**Документация:** https://sharp.pixelplumbing.com/  
**Как используем в проекте:** Преобразование изображений (WebP / JPEG → PNG) перед кодированием в KTX2 (toktx принимает только PNG и JPEG, но WebP обрабатываем через sharp в PNG).  
**Издатель:** Lovell Fuller

**Ключевые гарантии / поведение:**

- **Что делает:** Быстрая обработка изображений (resize, rotate, crop, format conversion, colour space correction).

- **Форматы:** Входные — JPEG, PNG, WebP, GIF, AVIF, TIFF; выходные — JPEG, PNG, WebP, GIF, AVIF, TIFF.

- **Точность:** Использует libvips, Lanczos resampling. Качество — high (сравнимо с ImageMagick).

- **Когда используется:** В нашем pipeline — только когда входная текстура WebP / JPEG, а нужно PNG для toktx:
  ```
  if (mime === 'image/webp' || mime === 'image/jpeg') {
    const png = await sharp(Buffer.from(tex.getImage())).png().toBuffer();
  }
  ```

- **Потеря качества:** Минимальна при выводе PNG (без сжатия). WebP → PNG — может быть потеря цвета из-за разных colorspace, но в локальном режиме это маловероятно.

**Для нашей валидации:**

- Может изменить геометрию: **Нет**, это только обработка пикселей.
- Потеря данных: **Minor** (зависит от исходного формата; PNG → PNG → безопасно).
- Гарантия: размеры изображения, метаданные RGB/RGBA остаются.

**Источники:**
- https://sharp.pixelplumbing.com/
- https://sharp.pixelplumbing.com/api-constructor (API reference)

**Издатель:** Guy Bedford (тот же автор, что у SystemJS)  

**Почему он, а не AST-парсер:** лексер уже лежит в дереве зависимостей как
транзитивная зависимость vitest — то есть им ровно Vite и разбирает импорты.
Полный AST-парсер (acorn / @babel/parser / oxc-parser) в дереве ОТСУТСТВУЕТ
(проверено 2026-08-03: `npm ls` пусто), а тащить его ради извлечения строк
`import` — новая зависимость против принципа «не выдумываем из головы»
(§0 ЗАВИСИМОСТИ.md).

**Ключевые гарантии / поведение:**

- **Что умеет:** извлекает спецификаторы всех `import`/`export`-форм, включая
  динамические `import(...)` с литеральным аргументом, `export * from`,
  многострочные импорты, кавычки, комментарии.
- **Что не умеет (принципиально):** `import(variable)` с динамическим
  спецификатором статически неразрешим — лексер вернёт `n === undefined`.
  Это не баг лексера, а свойство задачи: адрес зависит от значения переменной.
  В нашем коде таких импортов нет, гейт layer-boundaries явно это проверяет
  (запись со `specifier === null` считается нарушением).
- **Использование:** `await init()` один раз, затем `parse(source, filename)`
  → `[imports, exports]`; у каждой записи поле `n` — спецификатор, `d >= 0`
  означает динамический импорт.

**Для нашей валидации:**

- Прямая devDependency зафиксирована в `package.json` (до этого была только
  транзитивной у vitest) — прямой импорт в тестах без «магического» наличия.
- При обновлении vitest версия лексера может уехать вперёд — обновлять
  запись в этой секции по стандартному процессу (§0a).

**Источники:**
- https://github.com/guybedford/es-module-lexer
- Тот же пакет, что использует Vite (см. package.json vitest → es-module-lexer)

### Компонент: typescript (v7.0.2) + @types/node (v26.2.0) — devDependency (сборка ядра)

**GitHub:** https://github.com/microsoft/TypeScript · https://github.com/DefinitelyTyped/DefinitelyTyped  
**Версия в проекте:** typescript 7.0.2 (с 2026-08-10), @types/node 26.2.0 (с 2026-08-11)  
**Документация:** https://www.typescriptlang.org/tsconfig  
**Как используем в проекте:** компилируем `core/**/*.mts` в `.mjs` РЯДОМ с источником, под
тем же именем. Настройка — `tsconfig.json` (там же расписано, почему не отдельный `outDir`).
Запуск: `npm run build`, он же висит на `prepare`; проверка без записи — `npm run typecheck`.  
**Издатель:** Microsoft (TypeScript), сообщество DefinitelyTyped (@types/node)  

**Почему devDependency, а не dependency:** в готовом приложении TypeScript не участвует —
на диск и в установщик едет собранный JavaScript. Исходники `.mts` в пакет не кладутся
(`!core/**/*.mts` в `build.files`).

**Ключевые гарантии / поведение:**

- **`noEmitOnError`** — ошибка типа не оставляет на диске половину модуля. Важно именно при
  сборке рядом с источником: иначе приложение поднялось бы на предыдущей версии файла, и
  причина отказа была бы не та.
- **`verbatimModuleSyntax`** — импорт типа обязан быть записан как `import type`. Без него
  после стирания типов остаётся импорт несуществующего значения: отказ во время работы,
  которого компилятор не видел.
- **`declaration`** — рядом кладётся `.d.mts`, поэтому JSDoc-ссылки из оставшегося
  JavaScript (`import('./types.mjs').Addon`) продолжают разрешаться.
- **`types: ["node"]` объявлен явно.** Автоподхват пакетов из `node_modules/@types` в этой
  связке НЕ сработал: 2026-08-11 первый же `import path from 'node:path'` не собрался при
  установленном `@types/node`. С явным списком собирается.

**Что стоит знать при обновлении:**

- Переключение мажорной версии компилятора меняет собранный код (оформление, иногда
  используемые возможности среды). Перед принятием — сверить собранное с предыдущим,
  как это делалось при переводе каждого модуля: разница должна быть только в оформлении.
- `@types/node` тянется к версии Node, на которой идут тесты (20/22/24 в CI). Уехавшие
  вперёд типы могут описывать API, которого на Node 20 нет, — это увидит `npm run typecheck`,
  а не прогон.

**Источники:**
- https://www.typescriptlang.org/tsconfig
- https://www.typescriptlang.org/docs/handbook/modules/reference.html

### Компонент: @types/three (v0.185.0) — devDependency (типы просмотрщика)

**GitHub:** https://github.com/DefinitelyTyped/DefinitelyTyped  
**Версия в проекте:** 0.185.0 (с 2026-08-11) — тот же номер, что и у самой three  
**Как используем в проекте:** типы для `ui/viewer/*.ts`. Сам пакет `three` типов НЕ везёт
(в 0.185.1 нет ни поля `types`, ни единого `.d.ts`), поэтому без этого пакета браузерный

**Издатель:** сообщество DefinitelyTyped

Исходники интерфейса тоже не едут (`!ui/**/*.ts` в `build.files`).

**Ключевые гарантии / поведение:**

- **Номер версии обязан совпадать с three.** Типы описывают конкретный выпуск; при

**Что стоит знать при обновлении:** обновлять вместе с `three`, одним шагом. Мажорных
номеров у three нет — ломающие изменения приезжают с минорными, и типы их отражают:
несовпадение вылезет как ошибка сборки интерфейса, а не как поломка на экране.

### Компонент: @needle-tools/three-animation-pointer (v1.1.2) — плагин просмотрщика

**GitHub:** https://github.com/needle-tools/three-animation-pointer
**Версия в проекте:** 1.1.2 (с 2026-08-14)
**Как используем в проекте:** одна регистрация в `ui/viewer/viewer.ts` — плагин к
`GLTFLoader`, который учит просмотрщик показывать `KHR_animation_pointer`.
**Издатель:** Needle Tools (needle.tools)
**Лицензия:** MIT. Зависимостей времени выполнения ноль; peer — `three >= 0.165.0`
(у нас 0.185.1). На диске ~60 КБ, при том что сама three занимает 25 МБ.

**Зачем понадобился.** Обычный канал анимации адресует узел сцены. Канал по указателю
адресует место в JSON — «яркость материала 2», «поворот развёртки текстуры». Загрузчик
three.js такие каналы выбрасывает молча (`if (target.node === undefined) continue`), и
модель приезжает с пустым клипом: снаружи неотличимо от модели без анимации. Для нас это
была слепая зона — дефект со съехавшими указателями после схлопывания одинаковых текстур
проверялся только чтением JSON.

**Насколько это официально.** Плагин назван в документации самой three.js как
поддерживаемый внешний, и на нём построен официальный пример three.js
(`webgl_loader_gltf_animation_pointer`). Это лучший знак качества, какой бывает у
стороннего кода, но это не код mrdoob.

**Ключевые гарантии / поведение (проверено по исходнику 2026-08-14):**

- **Это ФОРК метода `GLTFLoader.loadAnimation`** — «MOSTLY DUPLICATE» в его собственном
  комментарии. Значит копия может разойтись с оригиналом при обновлении three.
- **Патчит `THREE.PropertyBinding.findNode` глобально.** Патч ЛЕНИВЫЙ: ставится только
  когда в модели реально встретился канал по указателю; обычных моделей не касается.
- **Перехватывает только пути `.materials.`, `.nodes.`, `.lights.`, `.cameras.`** —
  всё остальное уходит в исходную функцию. Обычные дорожки («Cube.position») под эти
  префиксы не подпадают, столкновения нет.
- **Слоты текстур поддержаны не все.** В коде явный TODO: `repeat`/`offset` живут только
  у `.map` и `.emissiveMap`. Указатель на `metallicRoughnessTexture` создаст дорожку,
  которую three.js не свяжет, и напишет в консоль `Trying to update property … but it
  wasn't found`. Это ограничение самой three.js, а не плагина: у неё одна развёртка на
  материал.
- **Типы TypeScript в пакете есть** (`types/index.d.ts`).

**Что стоит знать при обновлении:** сверять вместе с three — из-за форка `loadAnimation`.
Сторож — два браузерных теста на `Animated Pointer 01.glb`
(`tests/viewer-regression.browser.test.mjs`): они проверяют не число клипов, а наличие
дорожек и то, что цвет материала реально едет во времени. Проверено фальсификацией:
снимаешь регистрацию плагина — оба краснеют.

**Границы применения:** плагин живёт ТОЛЬКО в показе (`ui/viewer/`). Ядро, аддоны и
профили площадок про него не знают и знать не должны — см. `docs/ARCHITECTURE.md` §4g.

**Источники:**
- https://www.npmjs.com/package/@needle-tools/three-animation-pointer

### Компонент: three-gltf-extensions (v0.0.15) — плагины просмотрщика

**GitHub:** https://github.com/takahirox/three-gltf-extensions
**Версия в проекте:** 0.0.15 (с 2026-08-15)
**Как используем в проекте:** одна регистрация в `ui/viewer/viewer.ts` — плагин
`KHR_materials_variants`. Остальные плагины пакета не подключены.
**Издатель:** Takahiro (takahirox), один из мейнтейнеров three.js
**Лицензия:** MIT. Зависимостей времени выполнения ноль; peer — `three`. На диске ~62 КБ
на весь пакет, из них нужный плагин 8,6 КБ.

**Зачем понадобился.** Варианты материала — запасные цвета и отделки, между которыми
модель умеет переключаться: три окраски машины, четыре отделки часов. Загрузчик three.js
это расширение не читает вовсе, и художник видел ОДИН вид из трёх, ничего не зная про
остальные. Замер на корпусе: `CarConcept` — 3 окраски на 25 примитивах,
`ChronographWatch` — 4 отделки на 7.

**Насколько это официально.** Репозиторий назван в документации самого `GLTFLoader`
(блок «дополнительные расширения» в шапке файла) — там же, где и плагин указателя
анимации. Автор — мейнтейнер three.js. Это не код mrdoob, но и не случайная находка.

**Ключевые гарантии / поведение (проверено по исходнику 2026-08-15):**

- **Плагин `afterRoot`, а не форк загрузчика.** В отличие от плагина указателя анимации
  он ничего в three.js не переопределяет: дочитывает готовый результат и вешает на него
  `gltf.userData.variants` (имена) и `gltf.functions.selectVariant` (переключатель).
  Значит риск разъехаться с новой версией three.js у него заметно ниже.
- **Материалы вариантов грузятся ЛЕНИВО** — при первом переключении, через
  `parser.getDependency('material', i)`. Модель с четырьмя отделками не тянет вчетверо
  больше текстур, пока человек их не посмотрел.
- **Одинаковые имена вариантов разводятся суффиксом** (`Red`, `Red.1`): спецификация
  дубликаты разрешает, плагин делает имена уникальными. Имена приходят из файла и
  переводу не подлежат (Правило 8: это данные, а не интерфейс).
- **Переключатель замкнут на parser КОНКРЕТНОЙ загрузки.** Пережить смену модели он не
  может, и мы снимаем его в `_disposeModel` вместе с моделью.
- **Типов не везёт.** Пакет на чистом JS; узкое объявление — `ui/viewer/vendor.d.ts`,
  описано ровно то, чем пользуемся.

**Границы применения:** плагин живёт ТОЛЬКО в показе (`ui/viewer/`) — это свойство
показа, а не оптимизации: выходной GLB он не меняет ни на байт. За сохранность самих
вариантов при оптимизации отвечает движок (`tests/variants-survive.test.mjs`), и от
этого пакета она не зависит. Гейт границ — `tests/architecture/layer-boundaries.test.mjs`.

## Выводы для валидации (baseline metrics)

Из анализа выше следует:

1. **Структурные метрики НЕ меняются** при сжатии (Draco, Meshopt, KTX2):
   - Количество треугольников (при условии что не используется simplify/decimation).
   - Количество вершин, узлов, примитивов, материалов, сцен, анимаций, скинов.
   - Иерархия сцены.

2. **Меняются ТОЛЬКО** (в рамках baseline):
   - Размер на диске (fileBytes) — объект сжатия.
   - Размер в VRAM (gpuBytes) — особенно при KTX2.
   - Потенциально: количество текстур (если используется dedup / prune).

3. **Поэтому** baseline-checkpoint (BASELINE_METRICS в `addons/gltf/metrics.mjs`, начиная с рефактора core/addon; движок читает их через `gltfAddon.BASELINE_METRICS`) содержит:
   ```
   triangles, vertices, drawCalls, skins (действующие), nodes, animations
   ```

   И НЕ содержит fileBytes / gpuBytes / textureBytes, которым разрешено меняться.

   `vertices` — МЯГКИЙ ключ (`BASELINE_SOFT`): его расхождение даёт ℹ (инфо), но НЕ блокирует запись — Draco сваривает вершины при сериализации, меняя их число, при сохранной топологии/треугольниках; для анимированных моделей структуру защищают жёсткие ключи (skins, animations). Остальные ключи — жёсткие (расхождение = ❌, файл не пишется).

4. **Для будущих расширений** (decimation, simplify и др.): любое расширение, которое меняет жёсткий BASELINE_METRICS, будет автоматически заблокировано валидацией на фазе 4 (ВАЛИДАЦИЯ).
