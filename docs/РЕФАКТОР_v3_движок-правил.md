# glb_web_optimize v3 — рефактор в «движок + правила» (спецификация для реализации)

> **Назначение файла.** Это чертёж для того, кто будет писать код (Fable 5). Здесь —
> логика и форма, НЕ реализация. Цель шага: перестроить `optimize2.mjs` изнутри в
> «движок + массив правил», сохранив ТО ЖЕ поведение, ТОТ ЖЕ запуск (`node optimize2.mjs`),
> ТЕ ЖЕ флаги и результат. Это первый шаг «выращивания» к большой архитектуре
> (см. `ARCHITECTURE.md`), но всё ещё один файл на JavaScript, без монорепо и без TypeScript.
>
> **Железное правило шага:** после рефактора вывод на модели-роутере должен быть
> эквивалентен текущему v2 (те же удаления, те же цифры, тот же итоговый .glb). Рефактор
> меняет ФОРМУ кода, а не ЧТО он делает.

---

## 1. Зачем это (в одном абзаце)

Сейчас вся логика зашита в одну большую функцию `processFile`: проверки и фиксы идут
подряд, вперемешку, править их страшно. После рефактора каждое действие — самостоятельный
объект-правило в массиве, а `processFile` превращается в маленький движок, прогоняющий
правила по фазам. Добавить новую проверку станет = дописать один объект в массив, не
трогая движок. Это ровно форма из `ARCHITECTURE.md` (§4), но упрощённая под один файл.

---

## 2. Форма правила (прагматичная JS-версия)

Каждое правило — объект такой формы. Поля повторяют интерфейс `Rule` из большой
архитектуры, но без TypeScript и без лишнего на этом этапе.

```
rule = {
  meta: {
    id:            'geometry/orphan-vertices',   // "категория/имя", стабильный ключ
    category:      'geometry',                    // geometry|textures|materials|uv|attributes|scene|performance
    title:         'Висящие вершины',             // человекочитаемо, для отчёта
    severity:      'info',                         // error|warn|info — важность проблемы
    fixSafety:     'provable',                     // provable|numeric|perceptual|lossy — доказуемость безопасности
    runAfter:      ['geometry/weld'],             // зависимости: это правило идёт ПОСЛЕ перечисленных
    touches:       ['geometry'],                   // какие ресурсы трогает fix (для конфликтов в будущем)
    enabled:       (opts) => true,                 // включено ли при текущих флагах (напр. join выкл при --keep-parts)
  },

  // ФАЗА АНАЛИЗА. Только чтение. НИЧЕГО не меняет в документе.
  // Возвращает массив «находок» (findings) — что нашли и сколько.
  analyze(ctx) {
    // ctx.document — граф glTF-Transform; ctx.opts — флаги; ctx.inspect — кэш inspect()
    return [ { messageId, data, count } ];   // пусто [] если находить нечего
  },

  // Доказательство безопасности ДЛЯ ЭТОЙ находки на ЭТОМ файле.
  // Решает, применять ли fix автоматически. Причина всегда попадает в отчёт.
  canFix(finding, ctx) {
    return { safe: true, reason: 'структурно безопасно' };
    // safe:false → в отчёт в «Пропущено» с этой причиной, fix НЕ вызывается
  },

  // ФАЗА ПРИМЕНЕНИЯ. Меняет ctx.document (рабочую копию, не исходник).
  // Вызывается движком только если canFix вернул safe:true и fixSafety проходит по политике.
  fix(finding, ctx) {
    // применить нужную трансформацию glTF-Transform или свой проход
    return { detail: 'удалено 125 висящих вершин' };  // строка для «Применено» в отчёте
  },
}
```

### Две оси — важно (из ARCHITECTURE.md §2.2)

- `severity` = насколько плохо (для сортировки отчёта). НЕ решает, чинить ли.
- `fixSafety` = можно ли доказать безопасность (решает, чинить ли автоматом).
  Автофикс по умолчанию применяет только `provable` и `numeric`. `perceptual` (KTX2) —
  только если политика разрешает (сейчас разрешаем, т.к. пользователь выбрал UASTC и
  доволен). `lossy` — никогда автоматом.

## 3. Движок: пять фаз (заменяет тело processFile)

Движок ничего не знает о конкретных правилах — он работает с массивом `RULES`.

```
loadDocument(файл)                         → ctx.document + ctx.inspect (кэш) + snapshotBefore
                                             (исходный файл НЕ трогаем никогда)

ФАЗА 1 · АНАЛИЗ (только чтение)
    для каждого rule где meta.enabled(opts):
        findings += rule.analyze(ctx)       // собираем все находки, документ не меняется

ФАЗА 2 · ПЛАН
    отсортировать правила топологически по meta.runAfter (+ известный порядок пайплайна)
    для каждой находки с fix:
        d = rule.canFix(finding, ctx)
        если !d.safe            → в skipped(reason=d.reason)
        если fixSafety > политики → в skipped(reason='требует явного включения')
        иначе                    → в planned (в правильном порядке)

ФАЗА 3 · ПРИМЕНЕНИЕ (по порядку, меняем рабочую копию)
    для каждого planned:
        res = rule.fix(finding, ctx)
        applied += res.detail
    (в этой версии откат по-фиксно не делаем — оставляем задел на будущее, см. §7)

ФАЗА 4 · ВАЛИДАЦИЯ (весь ассет)
    инварианты: треугольники не изменились (кроме вырожденных), анимации/скины на месте,
                bounding box в пределах эпсилон, каждый материал резолвится
    gltf-validator: 0 ошибок
    если инвариант провалился → пометить в отчёте как ❌ и НЕ записывать .glb

ФАЗА 5 · ОТЧЁТ
    собрать метрики snapshotAfter, отрендерить отчёт (§5)
    записать .glb в output/ ТОЛЬКО если были applied и валидация прошла
```

Порядок пайплайна (жёсткий, кодируется через `runAfter`): dedup → prune → vertex-colors
→ weld → degenerate-triangles → orphan-vertices → (flatten+join) → prune → ktx2 →
geometry-compress. Это тот же порядок, что в v2 — не менять, он выверен.

## 4. Карта: текущее поведение → правила (ничего не потерять!)

Каждое действие нынешнего `optimize2.mjs` становится правилом. Таблица — контракт: всё
из левой колонки обязано сохраниться.

| Текущее действие в v2 | id правила | category | fixSafety | Заметки по логике |
|---|---|---|---|---|
| `dedup()` | `structure/dedup` | materials | provable | склейка дублей текстур/аксессоров |
| `prune()` (unused UV/attr/mat/tex) | `structure/prune-unused` | scene | provable | analyze считает, что удалится (сравнить semantics до/после — как сейчас) |
| белый COLOR_n → удалить; раскрашенный → warn/`--force` | `attributes/vertex-colors` | attributes | provable (белый) / lossy (раскрашенный) | canFix: белый→safe; раскрашенный→safe только при `--strip-vertex-colors` |
| `weld()` | `geometry/weld` | geometry | numeric | сварка идентичных вершин |
| вырожденные треугольники | `geometry/degenerate-triangles` | geometry | provable | runAfter: weld (weld их порождает) |
| висящие вершины (`compactPrimitive`) | `geometry/orphan-vertices` | geometry | provable | runAfter: weld; если функции нет в версии — warn и пропуск (как сейчас) |
| `flatten()`+`join()` | `scene/join` | scene | numeric | enabled: `!--keep-parts` |
| WebP/JPEG→PNG→KTX2, skip уже-KTX2 | `textures/ktx2` | textures | perceptual | enabled: `!--no-ktx` и toktx найден; analyze помечает уже-KTX2 как «пропущено» |
| `meshopt()` / `draco()` | `geometry/compress` | geometry | numeric | последним; кодек по флагу |

Ничего нового по функциям на этом шаге не добавляем — только переносим в новую форму.
(Новые правила из большого списка ТЗ — oversized textures, ORM packing, instancing и т.д.
— это следующие шаги, каждый = один новый объект в массиве.)

## 5. Новый отчёт (структура из твоего ТЗ)

Сейчас отчёт — плоские «Выполненные операции / Предупреждения / Safety». Приводим к
форме, которую ты описал: **Найдено → Пропущено (с причиной) → Применено → Валидация →
Оценка улучшений**. Отчёт рендерится централизованно из данных (findings/skipped/applied/
metrics), а не собирается правилами (ARCHITECTURE.md §2.3).

```
# Отчёт оптимизации — 1.glb
дата · кодек · политика фиксов

## Найдено (проблемы)
- ✓ 125 висящих вершин
- ✓ 18 вырожденных треугольников
- ✓ дубли текстур: 2
- ✓ неиспользуемый UV-канал TEXCOORD_1
- ✓ постоянный белый COLOR_0

## Пропущено (и почему)
- COLOR_0 меша X — реальная покраска, влияет на вид. Форсировать: --strip-vertex-colors
- Текстура orm — уже KTX2, повторно не кодируем

## Применено
- Удалены висящие вершины (125)
- Склеены дубли текстур (2)
- Сжата геометрия (meshopt)

## Валидация
- ✅ gltf-validator: 0 ошибок
- ✅ треугольники не изменились (кроме вырожденных)
- ✅ анимации сохранены · скины сохранены · иерархия цела

## Оценка улучшений
| | до | после |
| файл | … | … |
| VRAM (GPU) | … | … |
| draw calls | … | … |
| треугольники | … | … |
```

Формат `имя.report.md` рядом с моделью — как сейчас. Логи в `logs/` — оставить как есть.

## 6. Как это ложится в большую архитектуру (трассируемость)

Этот один файл — зародыш монорепо из `ARCHITECTURE.md`. Когда станет тесно, разрезаем по
готовым швам, без переписывания логики:

| Сейчас (один файл) | Потом (пакет из ARCHITECTURE.md) |
|---|---|
| массив `RULES` | `packages/rules/` (каждое правило → свой файл) |
| функция-движок (5 фаз) | `packages/core/` (engine + фаз-раннер + DAG) |
| функция-рендерер отчёта | `packages/reporters/` (md; позже json/html/sarif) |
| флаги + политика фиксов | `packages/profiles/` + конфиг-файл |
| `runCli`/toktx/meshopt | `packages/transforms/` (адаптеры) |
| snapshot + инварианты + validator | `packages/validate/` |

Момент перехода на TypeScript и монорепо: когда появятся внешние авторы правил или файл
перестанет помещаться в голове. Не раньше (ARCHITECTURE.md §7).

## 7. Заделы на будущее (НЕ реализовывать сейчас, но форму заложить)

Чтобы следующие шаги не требовали ломки:

- **Пофиксный откат.** Сейчас при провале инварианта просто не пишем файл. Форма `fix()`,
  возвращающего результат, оставляет место, чтобы позже откатывать конкретный фикс
  (snapshot перед каждым fix). Задел: движок уже разбит на фазы, добавить откат — локально.
- **Конфликты фиксов** через `meta.touches` — поле уже есть, детектор конфликтов добавится
  в фазу ПЛАН позже (сейчас правил мало и они не конфликтуют).
- **`--dry-run`** — прогнать фазы 1-2 и отчёт, пропустить фазы 3-5-запись. Тривиально при
  фазовом движке.
- **Профили-бюджеты** — сейчас политика фиксов = один флаг. Позже станет объектом-профилем
  (web/mobile/quest). `analyze` правил, читающих бюджеты (draw calls, VRAM), получит их из
  `ctx.profile`.
- **Оценки (scores)** — поле `penalty` в находках заложить необязательно; включим, когда
  правил станет достаточно (ARCHITECTURE.md §2.7).

## 8. Границы шага (для того, кто пишет код)

**Делать:**
1. Ввести массив `RULES` и перенести в него все действия из таблицы §4 без изменения логики.
2. Переписать `processFile` как движок из §3 (5 фаз над `RULES`).
3. Централизовать сборку отчёта в форму §5.
4. Сохранить: все флаги (`draco`, `--keep-parts`, `--no-ktx`, `--strip-vertex-colors`),
   логи в `logs/`, ротацию логов, поиск toktx/CLI, декод WebP→PNG, пропуск уже-KTX2,
   правило «не трогать исходник», пропуск уже готовых файлов в output.

**НЕ делать на этом шаге:**
- Не добавлять новые проверки/оптимизации (это следующие объекты в массиве, отдельные шаги).
- Не переходить на TypeScript.
- Не разбивать на пакеты/монорепо.
- Не менять поведение — только форму.

**Критерий приёмки:** `node optimize2.mjs` на роутере даёт эквивалентный v2 результат
(те же находки, те же удаления, валидный .glb, валидатор 0 ошибок), но отчёт — в новой
структуре §5, а код — в форме «движок + правила».

## 9. Порядок реализации (для Fable 5, пошагово, каждый шаг проверяем)

1. Каркас движка: массив `RULES` пустой, `processFile` = 5 фаз, отчёт-заглушка. Запуск не падает.
2. Перенести read-only находки в `analyze` правил (пока без fix) → «Найдено» и «Пропущено» наполняются, файл не меняется. Сверить находки с текущими.
3. Перенести фиксы в `fix` правил по одному, в порядке пайплайна §3, сверяя результат после каждого. Начать с `structure/dedup`, `structure/prune-unused`.
4. Подключить валидацию (§3 фаза 4) и новый отчёт (§5).
5. Прогон на роутере, сверка с v2. Обновить README (итерация v3) и `каталог скриптов.md`.

Старый `optimize2.mjs` (v2) сохранить копией до подтверждения, что v3 эквивалентен.
