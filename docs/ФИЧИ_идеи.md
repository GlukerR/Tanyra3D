# Идеи для фич — glb_web_optimize

> Пресеты, вьюверы, интеграции с платформами. Отсортировано по приоритету и слоям разработки.

---

## Пресеты и сохранение конфигураций

**Текущий статус:** Идея

- **Функция:** Пользователь выбирает настройки оптимизации один раз, система сохраняет как именованный пресет.
- **Примеры:** "Shopify Quick", "Three.js Web Optimal", "Mobile Conservative"
- **UI:** Вкладки в интерфейсе (как браузерные вкладки).
- **Слой:** v0.2+ (после первого MVP)

## Вьювер с поддержкой всех движков

**Текущий статус:** Концепт (частично используется существующий Three.js-просмотрщик)

- **Идея:** Вьювер показывает не только модель, но и все варианты сжатия/компрессии (Draco, Meshopt, UASTC, ETC1S).
- **Интерактивность:** Пользователь выбирает сжатие во вьювере → система говорит, какие движки его поддерживают.
  - Если выбрал Draco, но движок его не поддерживает → красный флаг + рекомендация переоптимизировать.
- **Примечание:** Вьювер Three.js уже переиспользуется (см. [[3D Viewer — Three.js просмотрщик GLB]]).
- **Слой:** v0.2+ (интеграция в web-interface)

## Вьювер с поддержкой экспорта под конкретные движки

**Текущий статус:** Концепт

- **Фича:** Вьювер не просто показывает модель, а позволяет выбрать целевой движок (Unity, Unreal, Three.js) и сразу видит, как модель будет выглядеть в его ограничениях.
- **Примеры:**
  - "Как это будет в Unreal?" → переключить на физику Unreal, шейдеры, лимиты.
  - "Как это будет на Quest?" → включить ограничения по VRAM, полигонам.
- **Слой:** v0.3+ (после базовой поддержки движков)

## Умная упаковка скачивания: ZIP только при 2+ файлах, отчёт — по умолчанию с быстрым отключением

**Текущий статус:** Идея, уточнена и готова к реализации

### Логика упаковки

- **По умолчанию скачивается:** файл модели + отчёт (before/after, бюджеты платформы, рекомендации по декодерам — см. следующий раздел). Это 2 файла → упаковываются в **ZIP**.
- **Если пользователь отключил отчёт** (см. переключатель ниже) — скачивается только файл модели, без архива, напрямую.
- **Правило общее:** архивировать в ZIP, когда файлов для скачивания 2 или больше (тот же принцип сработает и для будущих кейсов — несколько вариантов под разные платформы, несжатый `.gltf` с отдельными `.bin`/текстурами и т.д.). Один файл — скачивается как есть, без обёртки.

### Почему ZIP, а не RAR/7z

- **RAR** — проприетарный формат: нет нативной распаковки на macOS/Linux, лицензионные ограничения на программное создание архивов — несовместимо с открытым некоммерческим Apache-2.0 проектом.
- **7z** — требует системного бинарника `7z`, которого нет по умолчанию ни в одной ОС. Это ломает обещание v0.1.0: «просто `npm start`, ничего доустанавливать не нужно».
- **ZIP** — открывается нативно в Windows/macOS/Linux без установки чего-либо, в Node есть чистые JS-библиотеки без внешних зависимостей (`archiver`, `jszip`). Единственный вариант, совместимый с принципом «для обычных людей».
- **Важно:** реального сжатия ZIP почти не даёт — GLB и так уже содержит сжатую Draco-геометрию и KTX2-текстуры. Ценность архива не в экономии места, а в упаковке нескольких файлов в один клик.

### Переключатель отчёта — рядом с кнопкой скачивания

- **По умолчанию отчёт ВКЛЮЧЁН** — новый пользователь должен сразу видеть, что изменилось и почему.
- **Одним щелчком рядом с кнопкой экспорта/скачивания** — переключатель «Скачивать с отчётом» (вкл/выкл).
- **Назначение:** те, кто работает по знакомому, уже проверенному пайплайну регулярно, могут отключить отчёт и получать сразу файл модели без лишнего шага распаковки ZIP.
- Желательно запоминать выбор пользователя в рамках сессии (не обязательно через постоянное хранилище — важно, чтобы не приходилось переключать каждый раз заново в течение работы).

**Слой:** v0.1.0 (естественное расширение уже существующего экспорта и отчёта) — низкая цена реализации, высокая польза.

## Рекомендации по декодерам в отчёте (Draco / KTX2 → что нужно движку)

**Текущий статус:** Идея, уточнена и готова к реализации

### Проблема

Draco (сжатие геометрии) и KTX2/Basis Universal (сжатие текстур) не поддерживаются движками «из коробки» — их нужно явно подключать:

- **Three.js:** требует `DRACOLoader` (файлы `draco_decoder.wasm/js`) и `KTX2Loader` (transcoder-файлы Basis), зарегистрированные в загрузчике модели.
- Без этой настройки модель либо не загрузится с ошибкой, либо текстуры окажутся чёрными.

Это одна из самых частых причин путаницы у тех, кто сжал модель и не знает, что нужно донастроить на стороне движка.

### Как реализовать

- Если при оптимизации применён Draco и/или KTX2 — в отчёт добавляется секция **«Что нужно настроить на вашей стороне»**.
- Содержимое секции зависит от **выбранного профиля платформы**:
  - **Three.js / общий веб** — конкретный сниппет кода для подключения `DRACOLoader`/`KTX2Loader`.
  - **Shopify / другие платформы со встроенным вьювером** — нужно **проверить отдельно**, требуется ли что-то от пользователя, а не считать по умолчанию, что нужна ручная настройка (у них может быть уже всё подключено на их стороне).
  - **Quest / Mobile** — уточнить по тому же принципу, отдельно от Three.js-кейса.
- **Владелец:** секцию формирует `ai-assistant` (уже отвечает за объяснения решений); `core-engine` должен отдавать структурированные данные о том, какие именно оптимизации применены (Draco/KTX2/meshopt), чтобы `ai-assistant` мог опираться на факты, а не дублировать логику.

**Слой:** v0.1.0 (расширение существующего отчёта, не новая подсистема) — низкая цена, закрывает реальный (не гипотетический) риск для пользователя.

## SQLite для истории аудита (ОТЛОЖЕНО — кандидат, не для v0.1.0)

**Статус:** Идея-кандидат, НЕ добавлять в архитектуру сейчас.

- **Суть:** локальная встраиваемая БД (один файл `.db`, без сервера) для истории проверок: список моделей, версии, результаты анализа, пресеты, ошибки. Модели в БД не хранятся — только пути к ним + метаданные.
- **Почему отложено:** противоречит принципу v0.1.0 «просто npm start, без лишних зависимостей». На этапе одиночной обработки у истории ещё нет потребителя.
- **Когда станет актуально:** batch-обработка, «недавние файлы», версии, baseline/regression-diff (уже заложен в ARCHITECTURE §10 как файловый — SQLite это альтернативная реализация той же потребности).
- **Правильная постановка решения:** не «нужен ли SQLite», а «файлы vs SQLite, и не раньше, чем появится batch/история». Для MVP файлы (JSON/md-отчёты) проще и уже вписаны в CI-историю проекта.
